Testing Phases

Phase A — Baseline Record system metrics with no load running. Establishes the normal operating state for comparison.
Phase B — Load Testing Run each application under stress. Record CPU, memory, disk, and network metrics simultaneously.
Phase C — Bottleneck Analysis Identify which resource becomes the limiting factor under each workload type.
Phase D — Optimisation Apply at least two improvements and re-measure to quantify the impact.

⚠️ Threat Model

Identifying specific security threats relevant to this Linux server deployment and planned mitigations.

Threat 1 — Brute Force SSH Attack
Description: Tools use millions of password guesses to breach port 22 to get unauthorised entry.
Likelihood: High – since port 22 will constantly be probed by anyone connecting to this server from the internet.
Impact: Total take-over of the entire system.
Mitigation:SSH key-based authentication, fail2ban, and a firewall that limits SSH to only workstation IP address.
Threat 2 — Privilege Escalation
Description: With limited access to the system, an attacker can leverage a misconfiguration or weakness in the kernel or sudo privileges to escalate to root.
Likelihood: Medium depending on the system configuration.
Impact: Total system control and data leakage, amongst others.
Mitigation: Principle of least privilege, restricting sudo permissions, unattended upgrades for security patches and AppArmor.
Threat 3 — Unauthorised Service Exposure
Description: Unnecessary services running on open ports expose additional attack surface — each service is a potential entry point.
Likelihood: Medium — default installations often enable unused services.
Impact: Lateral movement, data interception, denial of service.
Mitigation: UFW firewall denying all incoming by default, service audit to disable unnecessary services, nmap scanning to verify exposed ports.
Threat 4 — Unpatched Software Vulnerabilities
Description:Known CVEs in old versions of software can be used to remotely exploit systems without authentication.
Likelihood: Likely to happen eventually without updates being installed.
Impact:Code execution, data theft, system compromise.
Mitigation: Automatic security updates using unattended-upgrades, security testing with Lynis, manually checking for updates.

📝 Week 2 Reflection

This week was dedicated solely to planning and not implementing anything — thinking about the strategy prior to configuring anything. As with all professional practice, the focus is on carefully planned security, not reactive security.


One thing I realized from the threat modeling activity is that even a simple single-server environment would face multiple realistic threats. The most important thing I have learned from this week is the SSH brute force threat – which is guaranteed to occur in any connected computer, which means key authentication and fail2ban become essential rather than nice to haves.


Key insight: Performance vs security is a common tradeoff – for example, AppArmor causes some overhead on the CPU in order to restrict access. We will measure these tradeoffs in Week 6.
