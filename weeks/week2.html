Testing Phases

Phase A — Baseline Record system metrics with no load running. Establishes the normal operating state for comparison.
Phase B — Load Testing Run each application under stress. Record CPU, memory, disk, and network metrics simultaneously.

⚠️ Threat Model

Identifying specific security threats relevant to this Linux server deployment and planned mitigations.

Threat 1 — Brute Force SSH Attack
Description: Automated tools attempt thousands of password combinations against port 22 to gain unauthorised access.
Likelihood: High — port 22 is continuously scanned on any internet-facing system.
Impact: Full system compromise if successful.
Mitigation: Key-based authentication (disables password login), fail2ban to block repeated failures, firewall restricting SSH to workstation IP only.
Threat 2 — Privilege Escalation
Description: An attacker with limited access exploits misconfigured sudo rules or kernel vulnerabilities to gain root privileges.
Likelihood: Medium — depends on system configuration.
Impact: Complete system control, data exfiltration, persistent backdoor installation.
Mitigation: Principle of least privilege, restricted sudo access, regular security updates via unattended-upgrades, AppArmor to confine processes.
Threat 3 — Unauthorised Service Exposure
Description: Unnecessary services running on open ports expose additional attack surface — each service is a potential entry point.
Likelihood: Medium — default installations often enable unused services.
Impact: Lateral movement, data interception, denial of service.
Mitigation: UFW firewall denying all incoming by default, service audit to disable unnecessary services, nmap scanning to verify exposed ports.
Threat 4 — Unpatched Software Vulnerabilities
Description: Known CVEs in outdated packages can be exploited remotely without authentication in some cases.
Likelihood: High over time if updates are not applied.
Impact: Remote code execution, data breach, system takeover.
Mitigation: Automatic security updates via unattended-upgrades, Lynis security auditing, regular manual update checks.

📝 Week 2 Reflection

This week focused entirely on planning rather than implementation — designing the security approach before touching any configuration files. This mirrors professional practice where security is planned systematically rather than added reactively.


The threat modelling exercise highlighted that even a simple single-server deployment faces multiple realistic attack vectors. The most critical finding is that SSH brute force is essentially guaranteed on any networked system, making key-based authentication and fail2ban non-optional controls rather than optional extras.


Key insight: Security and performance are often in tension — for example, AppArmor adds a small CPU overhead to enforce access controls. These trade-offs will be quantified and analysed in Week 6.
